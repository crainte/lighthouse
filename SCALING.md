# Scaling Warden to 10,000 Checks

## Goal

Warden should reliably monitor at least 10,000 checks across a geographically distributed deployment without trying to reproduce Prometheus's feature set. The target is dependable wide-area probing, clear regional and global state, bounded failure behavior, and predictable operation during outages and coordinator recovery.

The expected topology is:

```text
Global coordinator cluster (3 nodes)
  ├── Regional coordinator cluster: US (3 nodes)
  │     └── Agents in multiple failure domains
  ├── Regional coordinator cluster: TW (3 nodes)
  │     └── Agents in multiple failure domains
  ├── Regional coordinator cluster: ZH (3 nodes)
  │     └── Agents in multiple failure domains
  └── Regional coordinator cluster: EU (3 nodes)
        └── Agents in multiple failure domains
```

A typical Kubernetes cluster may run three agent replicas for capacity, rolling upgrades, and failover. Those colocated replicas normally belong to the same Warden zone and use placement `count = 1`: one agent probes a given check while rendezvous hashing spreads checks across all three. Distinct zones or regions provide independent observations and multiply result volume.

## Confirmed identity decisions

- Checks use immutable UUIDv7 identifiers generated by the Rust application.
- DuckDB stores check identifiers in its native `UUID` type.
- Check names are mutable Unicode display values, not identifiers.
- File-seeded checks are removed. Checks are created through the authenticated control plane.
- One logical check keeps the same UUID in every region.
- The global control plane generates an ID before distributing a new check. Regions never generate separate IDs for the same global check.
- Regional-only creation generates an ID at the receiving regional coordinator and preserves it if later imported globally.
- API routes, storage relationships, agent assignments/results, placement, dependencies, maintenance, incidents, notifications, replication, and global aggregation use UUIDs.
- Human-facing responses carry both `check_id` and `name`. Notifications display the name but use the UUID for deduplication.
- Check names should remain unique initially for operator clarity, although uniqueness is a product rule rather than identity.
- Existing pre-release DuckDB files may be treated as incompatible; no name-to-UUID compatibility layer is required.

## Capacity model

The important unit is an observation, not an installed agent:

```text
results per second = checks × selected observation domains ÷ interval seconds
```

At 10,000 checks and a 30-second cadence:

| Placement | Results/s | Results/day | Results/30 days |
|---|---:|---:|---:|
| One selected agent in one domain | 333 | 28.8M | 864M |
| Three agents all probing every check | 1,000 | 86.4M | 2.592B |
| One selected agent in five domains | 1,667 | 144M | 4.32B |

Three colocated agents with `count = 1` divide 10,000 checks into approximately 3,333 checks each, averaging roughly 111 probes/s per agent at a 30-second cadence. Adding replicas to the same domain improves capacity and failover without increasing logical observations. Adding independent domains deliberately increases observations, storage, replication, and query work.

Three-node regional full replication multiplies physical storage and write work by three. At one observation per check per region, every regional database retains 864M rows for 30 days, while the region operates three physical copies.

The UI's 90-day maximum does not by itself bound ingestion, replication, retention deletion, checkpoints, backups, global summaries, or broad queries. Current raw-result retention defaults to 30 days; 90-day uptime can use compact state transitions instead of raw observations.

## Polling and scheduling audit

`uptime-monitor-design.md` correctly specifies one independent async task per check and batched result posting. Tokio task count is not the primary concern: thousands of sleeping tasks are reasonable.

The implementation now uses cron schedules aligned to wall-clock boundaries. Thousands of checks with `*/30 * * * * *` can wake together at seconds 00 and 30. The resulting synchronized network, DNS, TLS, socket, CPU, and result-ingest burst is the scaling risk, particularly when targets time out during a shared outage.

The design document's older interval examples imply naturally staggered timers and do not describe this cron synchronization. It also estimates only up to 5,000 checks and does not establish a 10,000-check envelope.

Required scheduler work:

1. Preserve exact calendar semantics for genuinely calendar-bound cron expressions.
2. Deterministically spread interval-like schedules using a stable phase derived from the check UUID.
3. Bound concurrent probes with a semaphore or scheduler queue; do not silently discard due work.
4. Measure scheduling delay separately from target latency.
5. Expose queued probes, in-flight probes, schedule-delay percentiles, timeout counts, and dropped result batches.
6. Capacity-test healthy operation and mass timeout behavior separately.

A complete worker-pool rewrite is not automatically required. Per-check tasks plus deterministic spreading and a shared concurrency permit may preserve the simple isolation model while controlling resource use.

## Current protocol behavior

### Agent to regional coordinator

Agents poll for assignments every 10 seconds by default. Each poll currently causes the coordinator to load/deserialise all checks, reconstruct fleet state, recompute rendezvous placement across all checks, and return the agent's full assigned configuration even when nothing changed.

Results are already incremental and batched every five seconds. Failed batches are retried in a bounded queue, but retries use a fixed cadence and payloads are uncompressed JSON.

Required changes:

- Cache check definitions and placement plans in memory.
- Recompute placement only when checks, credentials, capabilities, topology, or liveness change.
- Introduce a configuration generation and conditional poll response.
- Return `304 Not Modified` or a small unchanged response when appropriate.
- Add `upsert` and `remove` deltas keyed by check UUID.
- Keep a full compressed snapshot for bootstrap and repair.
- Add explicit batch/body limits and useful oversized-batch errors.
- Add bounded exponential backoff with jitter for transport failures while continuing to run the last valid assignment.
- Avoid sending mutable presentation-only fields to agents unless probe execution needs them.

### Regional peer replication

New result/state/config data is generally sent incrementally, and anti-entropy can repair missed writes. Important weaknesses remain:

- Some peer fan-out loops are sequential, multiplying timeout latency by peer count.
- State-transition gossip can send one request per transition per peer.
- Fleet-presence snapshots are resent periodically even without changes.
- Replicated-result deduplication performs an anti-join without an efficient unique key/index.
- There is no transport compression.

### Alert identity conflict health and safe repair

`warden_replication_alert_identity_conflicts_total` is a per-process counter of
replicated alert IDs whose immutable payload differs from an existing local row.
It is intentionally a health alarm, not a reconciliation mechanism: the
coordinator retains the local row and continues applying the rest of the batch.
A non-zero value means legacy divergent alert rows remain and should be alerted
on; a rising value after a restart or deploy means the divergence is still being
replayed. The first observed conflict is logged at warning level with the peer
origin and alert IDs; repeated observations are debug logs to avoid an
anti-entropy log storm.

Repair only in a maintenance window, after preserving evidence. First stop or
quiesce replication writers, record the conflicting IDs, peer origins, and both
rows from each affected replica, and take verified checkpointed backups. Decide
the canonical event from the original transition evidence (state history,
incident linkage, and source coordinator logs); do not choose by arrival order.
Then apply the chosen correction consistently to every replica while replication
is stopped, preserving the alert ID only when the canonical event is known.
Restart replication, let anti-entropy run, and verify that alert payloads agree
on all peers and that the counter no longer increases. If the canonical event
cannot be established, preserve both source records in the incident evidence,
remove neither automatically, and restore/rebuild the affected replica from a
verified canonical snapshot before rejoining it. Never delete or overwrite an
immutable conflicting row merely to make the metric disappear.

Required changes:

- Fan out to peers concurrently with a bounded deadline.
- Batch transitions per ingest cycle.
- Make fleet liveness incremental or generation-based.
- Give observations a replay-safe identity or enforce an efficient uniqueness strategy.
- Maintain replication cursors/manifests incrementally rather than scanning raw history every minute.
- Preserve paged catch-up so recovery yields to live ingest.
- Expose replication lag, failed sends, catch-up rows/bytes, and time-to-convergence.

### Regional to global

The global tier correctly keeps no raw probe data and performs request-time regional history queries. Current region state publication sends a complete visible-check summary every few seconds. Every regional coordinator may send equivalent snapshots, and each global receiver reprocesses them.

At 10,000 checks, many regions, and three nodes on both tiers, this becomes avoidable all-to-all amplification.

Required changes:

- Define one logical ordered state stream per region.
- Send incremental check-state changes with sequence numbers.
- Acknowledge sequence positions and support replay from a cursor.
- Use full compressed snapshots only for bootstrap, detected gaps, and periodic repair.
- Avoid three equivalent publishers per regional cluster; use deterministic ownership with failover, not necessarily consensus leadership.
- Replicate received global state among global coordinators instead of requiring every regional node to publish every snapshot to every global node.
- Allow partial regional read results with explicit unavailable-region metadata where product semantics permit it.

## Transport choice

Do not adopt gRPC merely to make existing full snapshots binary. The dominant problems are semantic and remain under any transport:

- full snapshots instead of deltas;
- repeated placement computation;
- synchronized schedules;
- sequential fan-out;
- broad database scans;
- missing backpressure and compression.

The immediate transport plan is authenticated HTTP with:

- compression, preferably zstd or gzip;
- generations, ETags, sequence numbers, and cursors;
- bounded incremental batches;
- concurrent fan-out;
- deadlines and exponential backoff;
- explicit versioned wire DTOs;
- full-snapshot fallback for recovery.

Reconsider gRPC/protobuf if measurements later show a material need for long-lived bidirectional streams, HTTP/2 multiplexing across thousands of agents, or serialization CPU/bandwidth savings after the protocol is already incremental. A WebSocket, SSE stream, or HTTP long poll can provide incremental delivery without immediately adding a second server and schema toolchain.

## DuckDB assessment

Keep DuckDB for now, but correct the known algorithms before treating it as validated for 10,000 checks.

Native UUID should be adopted during the identity migration. It gives fixed 128-bit validated keys and avoids converting potentially billions of textual references later. UUIDv7 improves entity insertion locality, but does not organize probe results by observation time because every result for a check repeats the check's creation-time UUID. `ts_millis` remains the time-series key.

Known storage failure points:

1. One synchronous DuckDB connection is protected by a mutex shared by ingestion, API reads, retention, and replication.
2. DuckDB calls execute on Tokio worker threads rather than a dedicated blocking storage executor.
3. Result batches use row-by-row prepared inserts inside a transaction rather than DuckDB's bulk Appender/Arrow paths.
4. Current-status lookup scans raw results with a partitioned window operation.
5. Status assembly performs per-check state-history queries.
6. ~~Config anti-entropy repeatedly scans every row of the config tables.~~ Fixed: config digests, including the placement-scoped check digest, read connection-local watermarks rebuilt once on open and maintained per touched key inside the writing transaction.
7. Replication deduplication lacks a supporting uniqueness/index strategy.
8. Daily retention deletes millions of rows from one large table rather than dropping time partitions.
9. Single-check history and latency filtering rely on table organization/zone maps without a demonstrated large-data plan.
10. Long storage lock holds can delay unrelated ingest and HTTP processing.

Required storage changes before claiming 10,000-check support:

- Materialize complete current check status during ingest so status reads never scan raw results.
- Fetch uptime spans set-wise and constrain them to the requested window.
- Batch leaf/current-state/history updates in the result transaction.
- Move blocking database operations to a bounded storage executor and measure queue time.
- Benchmark the Appender or Arrow batches against current inserts.
- ~~Replace the config digest's full-table scan with maintained replication metadata.~~ Done.
- Establish efficient replay deduplication.
- Add time-bucket latency rollups.
- Use shorter raw retention than summary retention where appropriate.
- Investigate time-partitioned files/tables so retention drops whole partitions.
- Measure checkpoint, WAL, backup, restore, and peer catch-up behavior.

A future split may retain DuckDB for control/current-state analytics while moving raw observations to partitioned object or time-series storage. Make that decision from benchmark results, not from identifier datatype or check count alone.

## Data retention tiers

The current implementation and the target policy are deliberately separate. Today the
coordinator enforces:

| Data | Current policy |
|---|---|
| Raw observations | 30 days by default (`retention.results_days`), pruned daily |
| State transitions | The raw-results window; the latest/open span per check is retained |
| Alerts and resolved incidents | 90 days by default (`retention.alerts_days`); open incidents are retained |
| Current state | Retained while the check exists |
| Minute latency rollups | 90 days, derived from raw on ingest and replicated on their own anti-entropy stream |
| Hourly latency rollups | 13 months, same derivation and replication as the minute tier |
| WAL | DuckDB recovery state; no independent age-based retention promise |
| Backups | No built-in scheduler or retention; checkpointed offline copies are operator-managed |

The target policy for a large deployment is:

| Data | Target retention |
|---|---|
| Raw observations | 30 days initially; reduce only after rollup boundary semantics and peer recovery are implemented |
| Minute latency rollups | 90 days |
| Hourly latency rollups | 13 months |
| State transitions | At least 90 days, independently configurable from raw observations |
| Current state | Retained while the check exists |
| WAL | Bound by measured checkpoint behavior and a monitored size budget, not by deleting WAL files |
| Offline backups | Daily checkpointed snapshots managed externally; retain 7 daily, 4 weekly, and 12 monthly copies |

Raw retention supports detailed diagnosis. State transitions support exact time-weighted
uptime without retaining every successful probe. Rollups support bounded long-range
latency queries. The backup schedule is an operational starting point, not a built-in
Warden guarantee.

Minute/hour rollups replicate through their own digest and cursored backfill
(`/internal/backfill/latency-minute`, `-hour`), the same shape as the alert/incident/
tombstone streams, rather than only ever arriving as a side effect of raw-result
replication. This closes the gap that used to make a rollup unrecoverable once a peer
had been offline longer than raw retention: with no raw rows left to derive it from and
nothing shipping the summary itself, 60+ days of already-summarized history was lost on
that replica for good. A rollup row is a growing upsert, not an append-only event, so its
digest carries running totals of `attempts`/`up`/`latency_sum` alongside a count and the
newest bucket, and a backfilled row is merged with `GREATEST` per counter rather than
summed — the only combination that stays correct no matter how many times the same page
is replayed. See `storage::RollupDigest` and `rollup_merge_from_backfill_sql`.

What this changes about peer recovery: raw observations older than the source's own
retention horizon are still gone for good — nothing anti-entropy does can un-delete a row
neither replica holds, and that condition is now recorded as a durable, attributable
`raw_data_gaps` row (readable at `GET /api/v1/admin/raw-data-gaps`) instead of only a log
line and a counter. What is no longer lost is the *summarized* latency history for that
same window: the minute/hour rollups covering it replicate independently of the raw rows
they were built from, so a peer that missed the raw retention window can still recover
"what latency looked like" for it, even though it can never recover "what every individual
probe returned." The loss is bounded to raw probe-level detail, not the whole history.

Capacity is driven by independent observation domains, not colocated agent replicas:

```text
raw rows per database replica = checks × domains × 86,400 / cadence_seconds × raw_days
physical row-copies in a region = raw rows per replica × coordinator replicas
```

At 10,000 checks, a 30-second cadence, 30 raw days, and three fully replicated
coordinators:

| Domains | Sustained ingest | Rows per database replica | Regional physical row-copies |
|---:|---:|---:|---:|
| 1 | 333/s | 864M | 2.592B |
| 3 | 1,000/s | 2.592B | 7.776B |
| 5 | 1,667/s | 4.320B | 12.960B |

Disk and backup estimates must use measured representative data rather than an assumed
bytes-per-row constant. For a baseline with `measured_rows`, scale its checkpointed
file and backup sizes linearly for planning, then retain headroom for WAL and temporary
checkpoint/prune space:

```text
estimated bytes per replica = measured bytes × target rows / measured_rows
regional checkpointed bytes = estimated bytes per replica × coordinator replicas
```

This estimate is not a support claim: compression depends on probe metadata and data
distribution, while checkpoints and large deletes can require transient space.

Do not reduce raw retention until minute/hour rollups exist, latency queries select the
correct resolution across raw/rollup boundaries, and a peer older than raw retention has
an explicit snapshot-or-gap recovery path. Require time partitioning when a full-scale
retention run cannot drop one expiry unit within the maintenance budget without blocking
ingest or requiring excessive temporary disk. Require a separate raw-observation store
when measured single-replica ingest, concurrent query latency, checkpoint/backup time, or
storage growth exceeds the accepted production envelope after rollups and partitioning.

A peer offline longer than raw retention cannot recover complete raw history through
ordinary anti-entropy and must be restored from a snapshot/backup or explicitly accept a
gap. There is no snapshot-restore tooling yet, so today this means the gap: `raw_data_gaps`
records exactly which check and time range anti-entropy could not close, and the same
window's minute/hour rollups — which do replicate on their own — keep its summarized
latency history recoverable even though the raw observations behind it are not. See
"Data retention tiers" above.

### Pre-1.0 database policy

No in-place schema or identity migrations are supported before 1.0. A database
written by an older build is rebuilt, not migrated.

This is not the general "wire formats and storage shapes change freely"
stance restated — it is a narrower, specific problem. Check identity is
cluster-shared state: every node's copy of `checks`, `alerts`, results, and
history has to agree on what a given check *is*. A migration run node-locally
on startup cannot establish that agreement — each node converts its own
database on its own schedule, so replicas disagree about identity for as long
as the rollout takes, and anti-entropy has no way to reconcile "this is the
same check under two different ids" on its own.

Derived identifiers make a node-local migration actively unsafe rather than
merely temporarily inconsistent. An alert id is `<check_id>-<ts>-<state>`,
so it names its check twice: once in the id and once in the body. A migration
that rewrites `alerts.node_id` (the body) without also rewriting `alerts.id`
leaves a row whose id names the old check and whose body names the new one.
`upsert_alert` treats an alert as immutable once its id exists and refuses to
overwrite it, so two replicas that picked different ids for the same
logical alert never converge — anti-entropy re-offers the same page every
sweep, forever. This was measured in the live three-node dev cluster: 127
alert rows with identical ids and different `node_id` per node, all
permanently conflicting.

The supported answer is a rebuild: stop the node, remove its database file,
restart it. It re-replicates current configuration from its peers and
re-accumulates history from the retention window forward. That is cheap and
correct precisely because the project has no released state to preserve yet;
once it does, this policy is the thing that will need to change.

`Storage::open` enforces this rather than leaving it as an operational
convention: it applies its DDL to an in-memory reference connection and
diffs `information_schema.columns` against the database being opened. A
missing table or column fails with `bail!`, naming the table and column and
pointing back at this section, instead of crash-looping on an `ALTER TABLE`
DuckDB rejects or silently reading a row that never got the column. Extra
columns — a rollback onto a database a newer binary already touched — are
tolerated.

Rebuild procedure for a node that fails to open on a real deployment: stop
the node, move its database file aside (e.g. `/data/warden.duckdb` to
`/data/warden.duckdb.bak`), and restart it. It re-replicates current
configuration from its peers and re-accumulates history from the retention
window forward; global-tier config re-replicates the same way regional
peers do. Do not delete the moved-aside file until the rebuilt node has
caught up.

## UUIDv7 implementation plan

The identity migration must remain coherent across all components. Partial conversion would create checks whose configuration, results, incidents, or global summaries cannot be joined.

### Phase 1: types and schema

- Add the Rust `uuid` crate with UUIDv7 and serde support.
- Add immutable `id: Uuid` to check definitions.
- Change the `checks` primary key from `name VARCHAR` to `id UUID`.
- Change all check-reference columns to native UUID, including results, current state, agent beliefs, state history, incident attachments, notification queues, dependencies, maintenance associations, and check-specific policies.
- Keep `name VARCHAR NOT NULL UNIQUE` initially.
- Remove obsolete name-primary-key migration/backfill assumptions.
- Treat existing pre-release databases as incompatible and fail clearly on an old schema.

### Phase 2: coordinator and API identity

- Generate UUIDv7 once on check creation.
- Reject caller-selected IDs on public admin creation.
- Permit trusted internal distribution/replication to preserve an existing UUID.
- Key in-memory maps and placement hashing by UUID.
- Change all check routes to UUID path parameters.
- Allow edits to change the Unicode display name without moving identity or history.
- Return both `check_id` and `name` in relevant DTOs.
- Use IDs for check order lists, purge operations, and heartbeat URLs.

### Phase 3: agents and dependent resources

- Send IDs with assignments and report IDs in results.
- Keep names only where agents require them for logs or diagnostics.
- Store dependency and maintenance relationships by ID.
- Store incident attachments and origin checks by ID.
- Generate incident IDs independently rather than embedding check names.
- Display names in notification text while retaining check UUIDs as PagerDuty or equivalent deduplication keys.
- Ensure a rename does not reshuffle placement because rendezvous hashing uses the immutable UUID.

### Phase 4: global identity and control plane

- Make global creation generate one UUID before regional distribution.
- Preserve that UUID through regional config replication.
- Aggregate global state by UUID, never by mutable name.
- Carry UUID and name in regional summaries.
- Route drill-down requests by the UUID's known regional ownership.
- Replace generic best-effort write fan-out with an explicit, retryable global configuration operation.

### Phase 5: remove file-seeded checks

- Remove `Config.checks` and `[[checks]]` parsing.
- Remove coordinator first-boot check seeding.
- Start agents with no assignments until the first successful coordinator poll.
- Remove implicit demo checks from ordinary empty production databases; demo data must require an explicit mode/action.
- Keep process/deployment configuration in TOML/environment while application resources live in the authoritative control store.
- Provide API/CLI automation for idempotent check creation and updates.

### Phase 6: frontend

- Route and select checks by UUID.
- Render `name`, never `check_id`, as the normal label.
- Submit dependency and maintenance selections as UUIDs.
- Keep URLs stable across renames.
- Paginate/filter/virtualize views that may contain 10,000 checks.
- Preserve UUID visibility in diagnostics and copy controls.

### Phase 7: cleanup and verification

- Delete remaining name-as-identity assumptions.
- Add Unicode names, rename preservation, cross-region identity, placement stability, incident continuity, and notification deduplication tests.
- Update `uptime-monitor-design.md` schema and protocol examples.
- Validate all crates, frontend tests/build, and deployment configurations.

## Benchmark gate for 10,000 checks

A release should not claim 10,000-check support until it passes a repeatable benchmark with:

- 10,000 checks at 30-second cadence;
- representative HTTP, TCP, DNS, TLS, ICMP, and OpenMetrics proportions;
- healthy low-latency operation;
- shared target failure causing five-second timeouts;
- one, three, and five observation domains;
- three agents per domain with `count = 1`;
- three regional coordinators;
- 30 days of synthetic retained raw data;
- global state propagation;
- one coordinator offline for an hour and catching up;
- concurrent status, history, and latency requests;
- retention and checkpoint work during live ingest.

Record at minimum:

- probe schedule-delay p50/p95/p99/max;
- in-flight and queued probes;
- agent CPU, RSS, sockets, file descriptors, and ephemeral-port pressure;
- result queue depth, retry count, and dropped batches;
- ingest rows/s and batch p50/p95/p99/max;
- storage executor queue time and operation duration;
- status/history/latency endpoint p50/p95/p99;
- replication lag, bytes, errors, and convergence time;
- global state propagation latency and bytes;
- DuckDB, WAL, and rollup growth;
- retention, checkpoint, backup, restore, and peer catch-up durations.

### Measured capacity envelope

The numbers below were measured on 2026-09-18 with a release build on a 16-thread
x86_64 workstation with NVMe storage, running the ignored benchmarks in this
repository. They describe one coordinator replica, not a full regional cluster.

Coordinator ingest, 10,000 checks × 3 observation domains (30,000 rows per batch,
10 batches, `benchmark_sustained_coordinator_ingest`):

| Measurement | Result |
|---|---:|
| Sustained ingest | 37,222 rows/s |
| Batch p50 / p95 / max | 788 / 849 / 849 ms |

The steady-state requirement at that shape is 1,000 rows/s, so measured single-replica
ingest has roughly 37× headroom before evaluation, rollup, and persistence become the
constraint. A debug build reaches only ~3,600 rows/s; benchmark from a release build.

Storage, 10,000 checks × 3 domains × 2 days of retained raw data
(172.8M rows, `benchmark_representative_storage_capacity_baseline`):

| Measurement | Result |
|---|---:|
| Retained rows | 172,800,000 |
| Checkpointed database | 1.54 GB (8.9 bytes/row) |
| Single-check history p95 | 30 ms |
| Latency series p95 | 91 ms |
| Retention prune of 86.4M rows | 23.5 s |
| Checkpoint after prune | 2.1 s |
| Restore (open + full count) | 25.3 s |

Scaling raw retention linearly from that measurement gives the planning envelope:

| Domains | Raw days | Rows per replica | Estimated bytes per replica |
|---:|---:|---:|---:|
| 1 | 30 | 864M | ~7.7 GB |
| 3 | 30 | 2.592B | ~23 GB |
| 5 | 30 | 4.320B | ~39 GB |

Multiply by three for a fully replicated region, and keep headroom for WAL and
transient checkpoint/prune space. Daily retention removes roughly one day of raw rows;
at three domains that is ~86M rows per run, measured at 23.5 s, which is why monolithic
deletes remain acceptable at this scale and time partitioning is not yet required.

An isolated release-mode benchmark (`tests/release_benchmark.rs`) exercises actual HTTP
probes, three coordinator peers, global state, online retention of an expired sentinel,
and concurrent status/history/latency requests on fresh temporary databases.

The 10,000-check gate **passes** as of 2026-09-21, in a container with a 65,536
file-descriptor limit, 2,048 concurrent probes per agent, a 30-second cadence and
anti-entropy enabled. Three consecutive runs converged three peers and the global
node, and pruned the retention sentinel, in 43–63 s:

| Run | Ingested results/s | Concurrent reads/s | Read p50 / p95 | Wall clock |
|---|---:|---:|---:|---:|
| 1 | 785 | 646 | 1 / 3 ms | 63 s |
| 2 | 1,577 | 640 | 1 / 3 ms | 43 s |
| 3 | 1,147 | 704 | 0 / 3 ms | 60 s |

Getting there took four changes, each measured rather than assumed. Per-call-site
slow-job attribution (`Database::call` is `#[track_caller]`, and jobs over 250 ms log
their submitting line) is what identified them:

1. **One in-flight replication request per peer, coalescing behind it**
   (`src/coordinator/replication_out.rs`). Ingest used to spawn a post per batch per
   peer, so a busy node aimed an unbounded number of concurrent `/internal/replicate`
   requests at one receiver, all contending for its single `state_write` and database
   worker. Backpressure is now coalescing: while a post is in flight, everything
   produced for that peer folds into one batch.
2. **A data-plane request budget of 30 s, separate from the 5-second ping budget.**
   Abandoning a replication post at five seconds discarded work the peer was still
   committing and handed anti-entropy a repair for data that had arrived anyway.
3. **Set-based replicated result insertion.** Dedup was a correlated `WHERE NOT EXISTS`
   per row plus per-row watermark and latest-result maintenance; it now stages the batch
   and does one anti-join, one watermark merge, and one latest-result merge.
4. **Set-based replicated belief merge and bulk config stamp loading.** Per-row
   `agent_check_state` upserts and two point lookups per config entry were the remaining
   multi-second holds on the database worker.

Before those changes a 3,000-check run failed to converge with replication applies
holding the single database worker for up to 26 s; after them, the same shape passed
at 403 results/s, and 10,000 checks passed at 785–1,577 results/s.

Run the benchmark from a release build with a file-descriptor limit of at least 65,536
(the shell default of 1,024/4,096 causes `EMFILE`, including on DuckDB WAL files):

```
docker run --rm --ulimit nofile=65536:65536 \
  -v "$PWD/target/release/deps/release_benchmark-<hash>:/bench:ro" \
  -e WARDEN_BENCH_CHECKS=10000 -e WARDEN_BENCH_SECS=120 \
  -e WARDEN_BENCH_MAX_IN_FLIGHT_PROBES=2048 -e WARDEN_BENCH_MAX_DISK_MB=4096 \
  ubuntu:25.10 /bench --ignored --nocapture --test-threads 1
```

Do not use the existing global Compose volumes for this test.

### Regression-gated benchmarks: ingest, query latency, anti-entropy, retention, restart

The runs above measure and report; nothing failed the run if a change regressed them.
`tests/release_benchmark.rs` adds five further `#[ignore]`d benchmarks, each with a

### What the gate did not remove: dedup cost grows with retained history

The replicated-result anti-join is bounded by the batch's own minimum timestamp, which
is sound (a duplicate carries the staged row's exact timestamp, so nothing that could
match is excluded) and lets DuckDB prune by zone map. It does not make the probe
constant. `benchmark_replicated_dedup_against_retained_history` measures a live-shaped
500-row batch against a seeded table:

| Retained rows | Bounded p50 | Unbounded p50 |
|---:|---:|---:|
| 20M | 17 ms | 32 ms |
| 40M | 20 ms | 51 ms |

Bounding the probe by the batch's timestamp range only flattened the slope. Splitting
the batch on the per-check high-water mark removes it: a row newer than the newest one
held for its check cannot be a duplicate of anything, which in steady-state replication
is every row in the batch, so the history table is never probed at all. Only repair,
which replays old rows by definition, reaches the anti-join.

| Retained rows | Watermark split | Timestamp bound only | Unbounded |
|---:|---:|---:|---:|
| 20M | 17 ms | 17 ms | 32 ms |
| 40M | 16 ms | 20 ms | 51 ms |

Replication cost now depends on batch size alone. The remaining ~16 ms is staging 500
rows and merging the derived tables. `UNIQUE(check_id, agent_id, ts_millis)` with
`INSERT OR IGNORE` is no longer needed for the live path; it remains the option if
repair throughput ever becomes the constraint.

### Retention costs what it removes, not what it keeps

`prune` used to follow the raw-result delete with two full rebuilds —
`result_replication_watermarks` and `latest_check_results` — each scanning everything
that *survived*. Pruning one day out of thirty read the other twenty-nine. Neither is
necessary: a maximum above the cutoff cannot be changed by deleting below it, so only
`result_count` moves, by exactly what was removed per check; and `latest_check_results`
holds one row per check, so an entry is stale precisely when its own timestamp is below
the cutoff.

`benchmark_retention_prune_against_retained_history`, 1,000 checks, one window out of
thirty removed:

| Retained rows | Removed | Prune | Rebuilds it replaced |
|---:|---:|---:|---:|
| 20M | 10.0M (half) | 514 ms | 2,148 ms |
| 40M | 1.33M (1/30th) | 176 ms | 7,552 ms |

The second row is the shape of a daily run: 43× less work, and what remains scales with
rows removed rather than rows retained. Extrapolated to a 30-day three-domain replica
(2.6B rows, ~86M removed daily) that is ~11 s of delete instead of minutes of rebuild.

The delete itself is then sliced across 24 database jobs (`Coordinator::prune_in_slices`)
so the worker interleaves probes and reads between them. Slicing makes retention
interruptible, not cheaper: each slice is a committed deletion of a time range, so an
interrupted run leaves a consistent database with more to remove tomorrow.

### Measured status, page, and global-push cardinality

`benchmark_status_and_global_push_production_cardinality` at 10,000 checks and three
regions, re-measured against the paginated read path (`src/page.rs`,
`MAX_PAGE_SIZE = 1,000`; `?section=`/`?page=`/`?limit=` on `/api/v1/status`,
`/api/v1/uptime`, and `/api/v1/latency-points`):

| Path | p95 | Bytes |
|---|---:|---:|
| Regional `/api/v1/status` (default page, 100 checks) | 53 ms | 23.7 KB |
| Full status **page** (3 requests, default 100-check page) | 66 ms | 1.28 MB |
| Full status page at the page ceiling (3 requests, 1,000-check page) | 102 ms | 12.8 MB |
| Global push (per region, per interval) | 90 ms | 2.04 MB |
| Global `/api/v1/status` (default page, 100 checks) | 13 ms | 20.9 KB |

This replaces the earlier unpaginated measurement of 509 ms / 134.7 MB for a full page
load at this cardinality (see "Read path: the status page is not the status endpoint"

(`STATUS_PAGE_SIZE` in `frontend/src/App.svelte`) is 100, so the second row — 1.28 MB,
a 99% reduction — is what a browser actually requests today. The third row is the
ceiling every list route enforces regardless of what a client asks for
(`crate::page::MAX_PAGE_SIZE`); even a client that deliberately requests the largest
page the server allows costs an order of magnitude less than the old unbounded read,
and the response says explicitly, via `total_checks`/`has_more`, that there is more to
page through rather than silently truncating. The supported dashboard cardinality is no
longer far below the supported *monitoring* cardinality — a 10,000-check deployment
renders its default view in low hundreds of KB, and pagination or per-section filtering

all.

Still unmeasured, and therefore outside a full 10,000-check support claim:
representative multi-protocol targets, three and five observation domains, 30-day
retained data alongside live traffic, an hour-long peer outage/catch-up, and online
backup. The offline backup step copies a closed, checkpointed file and reported ~0 ms
because the filesystem performed a copy-on-write clone; treat backup duration as
unmeasured on filesystems without reflink support.

### Read path: the status page is not the status endpoint

`/api/v1/status` is one batched query whose cost is independent of check count, and the
benchmark above measures that endpoint. It is not what loading the page costs.

The page used to additionally fetch one uptime strip per visible check and one latency
sparkline per graph-enabled check, so a load was `1 + N + M` requests and as many jobs on
the single database worker:

| Checks on page | Requests | Worker jobs |
|---:|---:|---:|
| 11 | ~23 | ~22 |
| 500 | ~1,001 | ~1,000 |
| 10,000 | ~20,001 | ~20,000 |

At 10,000 checks this overruns the worker's 256-slot queue. Because `Database::call`
awaits on `send`, the overflow becomes backpressure on everything sharing that worker —
including result ingest. One operator loading the dashboard could therefore stall
ingestion, which no storage-layer measurement would reveal.

Two independent changes were required, and they fix different halves:

1. **Batch the endpoints.** Set-based `uptime_strips` and `latency_points_for` push the
   segment bucketing into DuckDB, so `check_results` is scanned once and returns at most
   one row per check per segment instead of N scans of raw rows. This takes a page load
   to a constant number of requests: status, strips, points.
2. **Bound the page.** Batching still computed and shipped every visible check's
   90-segment strip. A flat page listing thousands of checks is also unreadable, so the
   structural fix is a per-section display mode: `inline` expands as before, `page`
   renders a rolled-up tile linking to `#/group/<name>`. `/api/v1/uptime` and
   `/api/v1/latency-points` take `?section=<name>`; with no `section` they return the
   primary page's scope, which is loose checks plus inline sections only. Cost then
   scales with the section being viewed rather than with the size of the deployment.

Both display modes stay supported because they suit different sections — a three-check
section is better inline, and a three-hundred-check section is not. The consequence is
that the bound is **available rather than automatic**: a deployment that leaves every
section inline keeps the flat page's cost. That is an operator decision, so `SectionsAdmin`
warns above `INLINE_WARN_AT` checks rather than overriding the choice.

A tile carries **no history strip** — colour plus "12 checks · 1 down". Both come from
the rollup already on `/api/v1/status`, so a paged section adds nothing to the hot path.
A per-section strip would have been one folded query over state spans: cheap per section,
but paid by every visitor on every load to decorate a tile most never open.

Section rollups reuse `crate::rollup::RollupPolicy`, the same `Threshold`/quorum
mechanism that decides zone and region state, via `section_rollups` in
`coordinator/routes/public.rs`. The override key is `section:<name>` and the fallback is
`CHECK_DEFAULT`. A section is another node set; giving it a separate rule would mean two
answers to "when is this amber rather than red". The browser never folds a section state
itself — `frontend/src/lib/rollup.ts` mirrors the fold only to preview an unsaved policy.

The ignored `benchmark_status_and_global_push_production_cardinality` now measures the
three concurrent requests made by a full page load — status, uptime strips, and latency
points — and validates that both chart responses contain every configured check.

### Indexing evaluated and rejected at measured scale

The only indexes in the schema before this evaluation were two `UNIQUE` indexes that
exist purely as constraint-violation triggers in transaction-rollback tests
(`one_check_per_ts`, `reject_alert`) — not for read performance. Everything else,
including `check_results`, has none beyond what DuckDB builds automatically for
`PRIMARY KEY`/`UNIQUE` columns. This was a gap worth measuring, not assuming either
way: the bundled DuckDB is v1.5.4 (`duckdb = "1.10504.0"` in `Cargo.lock`), and its ART
indexes changed behavior significantly from the earlier versions the "indexes rebuild at
startup" folklore is based on — they are now serialized to disk and lazily deserialized,
so per DuckDB's own docs "having an index will not cause any slowdowns when opening an
existing database." `benchmark_check_results_check_id_ts_index_tradeoff` and
`benchmark_alert_incident_lookup_index_tradeoff` (both ignored) confirm that directly
rather than trust the docs unread, and measure the three candidates the TODO named.

**`check_results(check_id, ts_millis)`** — the candidate for `Storage::history` and
`Storage::latency_series`'s per-check filter. Measured at 80.64M rows (2,000 checks × 14
raw days × 30 s cadence), two runs:

| | No index | With index |
|---|---:|---:|
| Database file | 2.27 GB | 6.00 GB (2.6×) |
| Bulk seed (80.64M rows) | 126–131 s | 214–267 s (1.7–2.1×) |
| Reopen (closed, checkpointed) | 8.6–9.4 s | 8.5–9.0 s |
| `history` p50 / p95 | 6 / 7–64 ms | 5–6 / 7 ms |
| `latency_series` p50 / p95 | 13 / 17–20 ms | 13 / 15–17 ms |
| Sustained `persist_ingest` (20 rounds × 2,000 rows on top of the backlog) | 16.7k–35.6k rows/s | 20.5k–34.4k rows/s |

Reopen time is identical with or without the index, confirming the lazy-deserialization
claim for this DuckDB build — that specific old assumption is false here, and an index
is not a startup-cost concern at this scale. But the other half of the folklore holds:
the index costs 1.7–2.6× the storage and materially slows bulk writes, both highly
reproducible across runs. What it does *not* do, reproducibly, is speed up the reads it
was meant for — `history`/`latency_series` p50s are identical with or without it, and
the p95 spread (7–64 ms without an index) is noise from cache/row-group state between
runs, not a stable tail the index removes (the second run's no-index p95 was 7 ms, the
same as with the index). The reason is `Storage::history`'s own time bound: DuckDB's
automatic per-row-group zone map on `ts_millis` — monotonically appended, so highly
selective — already prunes most of the table before `check_id` is ever evaluated, at
these row counts, whether an index exists or not. **Decision: do not add it.** It has a
real, reproducible cost and no reproducible benefit at the row counts measured, which
cover roughly 9% of the single-domain 30-day envelope in "Current single-table capacity
baseline" above. The measurement that would reverse this: `history`/`latency_series`
p95 measured against a table near that full envelope (800M+ rows) exceeding an
operator-relevant bound *and* not fixable by narrowing the query window — sustained
ingest has roughly 37× headroom over the steady-state requirement per the capacity
envelope below, so a write-side regression alone would not be disqualifying; it is the
combination of file-size cost and absent read benefit that decides this.

**`alerts(ts_millis)`** (`recent_alerts`, `alerts_since`, the retention delete) and
**`incident_checks(check_id)`** (`open_incident_for`, `incidents_for_check`, whose
declared `PRIMARY KEY (incident_id, check_id)` does not lead with the column those
queries filter on) were both measured together, seeded at a deliberately pessimistic
upper bound — every check across a 10,000-check fleet flapping roughly daily for the
full 90-day default `alerts_days` retention (900,000 alerts, 45,000 incidents):

| | No index | With index |
|---|---:|---:|
| Database file | 66.9 MB | 118.5 MB (1.8×) |
| Bulk seed | 2.7–4.0 s | 5.7–5.8 s (1.5–2.1×) |
| Reopen | 69–77 ms | 67–80 ms |
| `recent_alerts` p95 | 5–9 ms | 6–10 ms |
| `alerts_since` p95 | 7 ms | 8 ms |
| `open_incident_for` p95 | 2–3 ms | 3–4 ms |
| `incidents_for_check` p95 | 8–9 ms | 11 ms |
| `insert_alert` (2,000 single-row calls) | 102–103 rows/s | 102–103 rows/s |

Both tables are bounded by `alerts_days` retention rather than raw observation volume —
even this pessimistic seed is two orders of magnitude smaller than `check_results` — and
a full scan over tens of thousands to under a million rows is already single-digit
milliseconds. The read differences across both variants are within run-to-run noise in
either direction; the file-size and bulk-write cost are consistent and one-sided; and
`insert_alert`'s single-row write cost is identical with the index present or absent,
because it is bound by DuckDB's per-statement commit overhead rather than by ART
maintenance — a separate, unaddressed cost this evaluation did not set out to fix.
**Decision: do not add either index.** The measurement that would reverse this is
`alerts_days` retention being raised by an order of magnitude or more (multi-million-row
alerts table) while `recent_alerts`/`alerts_since` p95 exceeds an operator-relevant
bound.

**`state_history`** is not a candidate at all: its declared `PRIMARY KEY (check_id,
since)` already leads with `check_id`, which is every filter this codebase issues
against it (`record_state`, `state_spans`, and the retention anti-join). DuckDB builds
an ART for every `PRIMARY KEY` automatically, so the index this TODO item asks about
already exists. `list_status` and `uptime_strips` scan the table unfiltered by
`check_id` because they want every check in one pass; a `check_id`-leading index cannot
help a query that does not filter on it, so there is nothing to add there either.

## Placement-scoped configuration

### The problem

A check's `placement` narrows where it *runs*. Nothing narrows where it is
*stored*. Admin writes driven from the global dashboard are fanned out to every
region so the fleet stays uniform, so every region holds the full document for
every check whether or not it will ever probe it.

Observed in the development stack: `unifi` and `upstream` both carry
`placement.regions = ["us"]`, and both full definitions — target, expectations,
everything — sit in `coordinator-tw`'s database. One of those targets embeds a
push credential in its query string. The `dns` check ships five expected A
records; `flood` names a private LAN address. None of it is needed in tw, and tw
was never asked to probe two of the five.

The costs, in order of seriousness:

1. **Distribution of secrets and topology.** A check document carries the target
   and, for HTTP, arbitrary request headers — which is where credentials live.
   Today they reach every region's database and are readable by anyone holding
   an admin session or agent credential in any of them. The objection is not to
   storing a probe credential in the cluster that probes with it; it is to that
   credential travelling to clusters that do not.
2. **Per-region cost proportional to the global catalogue.** Config
   anti-entropy reads every check document per sweep — measured at 0.64–2.2 s of
   database-worker time for 10,000 checks — and every region pays it for the
   whole fleet regardless of its own workload. `list_checks()` on each agent poll
   is O(total catalogue) for the same reason.
3. **Regional status pages list checks the region can never observe**, which
   read as permanently unmeasured because they are.

### The gap this exposes

Cross-region configuration has no repair at all. `fan_out_write` applies a write
region by region and returns on the first failure — after earlier regions have
already applied it — so a partial write is reported as an error and then never
reconciled. A region that is merely stale drops out of the endpoint list and
misses the write silently. Within a region, peers converge through config
digests; between regions, nothing does.

Answering "what should this region hold?" is therefore needed twice over: to
scope distribution, and to repair it.

### The shape

The global tier becomes authoritative for the catalogue — whole documents, which
is safe precisely because documents no longer carry secrets (below) — and
reconciles each region against the set its placement implies. The control plane gains a
dependency on the global tier, which is why that tier wants to be three nodes
rather than one; the data plane — probing, evaluation, rollup, incidents,
paging — stays entirely regional and is unaffected by a total global outage.

A global node is then close to *a coordinator that holds the catalogue but no
results*, so most of the machinery already exists: HLC-stamped config entries,
per-kind digests, cursored backfill, cluster membership, anti-entropy.

### Unplace is disable-shaped, not delete-shaped

Removing a check from a region must preserve its identity. Three existing
behaviours decide this:

- **Disable** (`enabled = false`) is an ordinary config edit: identity and
  history are preserved, and re-enabling reconnects everything.
- **Delete** writes a `config_tombstone`, which blocks resurrection only by
  last-writer-wins and is itself pruned at `max(results_days, alerts_days)`.
- **Recreation through the UI mints a fresh UUIDv7**, so delete-then-recreate
  produces a *different* check. The old results remain under the old id,
  queryable but orphaned, with no path from the UI to reattach them. Delete is
  therefore irreversible in practice — and that is identity minting doing it,
  not the tombstone.

So unplace must be its own verb: drop the local definition, keep the id, never
write a tombstone. A tombstone would replicate, and de-placing a check in one
region would delete it in the region that still probes it.

### History survives unplacement

Raw results are keyed by `check_id` and are untouched by configuration changes.
The status path already tolerates results whose definition is absent and filters
them from the page. Unplacing therefore makes a check's history invisible but
intact, and re-placing it under the same id brings it back with no plumbing.

Retention ages the gap out as it would any other history; a month of
unplacement against a thirty-day window leaves little behind, which is the
correct outcome rather than a limitation.

The *published* state is cleared on unplace, so a region stops asserting a state
for a check it no longer watches; the check reads as its `default_status` until
the first result after re-placement. Raw results are untouched either way.

### Cross-region dependency belongs to the global tier

`depends_on` is resolved locally: a dependent check looks up its upstream's open
incident in *its own* store. An upstream probed only in another region has no
open incident to find, so the dependent opens its own — the fan-out that
dependency joining exists to prevent.

Co-placing both ends is not a fix, because the upstream may be one that should
not be probed in the dependent's region at all. The global tier is the only
place both states are visible, and is already re-evaluating cross-region rollups
on every push, so that is where a cross-region edge is attributed.

Attribution is a global-tier concern only: regions are not given awareness of
dependencies they cannot resolve, and each keeps its own incident. Relaying a
"join this incident" instruction down would make incident membership a
two-writer problem, and buys nothing a region can act on.

Note this is a different axis from `RollupPolicy` and the region tree, which
describe how children fold into a parent's *state*. Dependency describes
*causation* — who to blame when several things fail together.

### Phases

| Phase | Work |
|---|---|
| 1 | Done. Global holds the catalogue and placement durably, replicated between global nodes using the coordinator's existing config plane |
| 2 | Done. Per-region reconciliation against the set placement implies, driving the existing local-only unplace verb — never delete — for whatever a region should no longer hold |
| 3 | Done. Probe detail is delivered only to placed regions; regional pages show only what they hold |
| 4 | Done. Global runs as three nodes |
| 5 | Done. Cross-region dependency attribution at the global tier |

Phase 1 landed with its scope deliberately narrower than "every `ConfigKind`":
the global store is authoritative for checks and sections only, the two kinds
that are "the catalogue" in the sense this document's example is about, and
that carry no secret a region must keep to itself. Notifiers, credentials and
rollup policies stay on the pre-Phase-1 all-region fan-out — see
`global::store`'s module doc for why each is a deliberate exclusion rather
than an oversight, and widen the authoritative set in Phase 2/3 rather than
inventing a second mechanism.

Phases 2 and 3 landed together, in `global::reconcile`: only `ConfigKind::Check`
is placement-scoped — sections carry no per-check rule and stay on the old
whole-kind push, which the module doc explains is deliberate rather than an
oversight left for later. Two things had to change together for this to be
subset-correct rather than merely subset-shaped:

- **The digest.** Comparing a *whole-catalogue* check digest against a region
  holding only its placed subset would report "behind" forever and re-page
  every check on every sweep — the amplification this document opens with,
  reintroduced one level up. `Storage::config_digest_for_region` computes the
  same count/max-stamp shape restricted to checks a region's placement
  admits, via a `check_placement_regions` projection maintained in
  `upsert_check` exactly the way the existing flat columns are — never a
  `config` JSON parse — so a converged region costs one digest comparison per
  sweep, not a catalogue read. Tombstones stay unscoped in that digest: an
  outright delete must reach every region regardless of placement, since
  nothing records a check's *past* placement to scope a delete against.
- **The repair.** A digest mismatch on the Check kind no longer triggers
  `push_kind`'s whole-table resend. `reconcile_checks` instead diffs two id
  sets — `Storage::check_ids_for_region` (this node's desired set) against
  `/internal/global/check-ids` (what the region actually holds, primary keys
  only) — and converges both directions: ids missing are pushed, ids the
  region should no longer hold are unplaced through the existing
  `DELETE /api/v1/admin/checks/:id/unplace` route, never deleted. `push_now`,
  the best-effort push right after an admin write, filters the same way
  before a region ever sees a check document, so a check placed to one region
  is never even transiently written to another's store.

Phase 3 fell out of Phase 2 rather than needing its own code: `status_handler`
and the admin check list already filter through `coord.inner.checks`/
`storage.list_checks()`, which now only contain what reconciliation placed
here, so a region's pages were already scoped to what it holds the moment it
stopped holding anything else. The global dashboard is unaffected — it merges
per-region pushes (`global::cache::aggregate`) keyed by check id, so a check
placed in exactly one region still appears exactly once globally, same as
before.

Phase 5 landed as a read-side pass over what `relay_merge` already builds for
`/api/v1/incidents` and `/api/v1/checks/:id/incidents`: same-check incidents
from different regions are folded into one group when their
`[started_at, resolved_at ?? now]` windows overlap, and a dependent's group is
attributed to an overlapping cross-region upstream group via `depends_on`,
which now rides along on `CheckSummary` for exactly this. Neither writes
anything — a regional incident record, and the flat `incidents` array both
already relayed from, are untouched; `group_and_attribute` in
`global::incidents` only adds a `"groups"` array alongside them. See that
module's doc comment for the exact window and attribution rules, and its
tests for both the "seconds apart, one group" and "later outage, new group"
cases the rule has to get right.

No migration or version-gating work is planned: the project is unreleased, so
wire formats and storage shapes change freely.

### Secrets are referenced, not carried

Wanting probe credentials to stay in their own region conflicts with wanting the
global tier to move a check between regions: whoever moves it needs the whole
document, and the document is where the credential is. Both halves are right, so
the premise between them is what has to go — a check document has no business
containing a secret in the first place.

The convention already exists everywhere else in this project. A peer token, a
global token, a provisioned agent credential: each is either an inline value for
a fixture or a *name* resolved locally, with a deliberate error when it cannot
be resolved. `ProvisionedCredential::resolved_token` is the shape, and its
sibling `missing_token_error` is the attitude — an unresolvable secret says so
loudly, because "no results" reads like "not scheduled yet" and this project
treats that as the dangerous failure.

Applied to checks, a target or header carries a reference and the region
resolves it at hand-off to its own agents. Three things follow:

- The document stops being sensitive, so the global tier can hold, distribute
  and move it freely. The conflict disappears rather than being traded off.
- The value never leaves the region that probes with it, which is what the
  coordinator cluster is *for*.
- Moving a check from one region to another becomes: the global hands over the
  document, and the receiving region reports the named credential as missing
  until an operator provisions it. Requiring an explicit act to give a new
  region a credential is the boundary, not friction to be smoothed away.

A useful consequence for the phases below: placement-scoped distribution stops
being a security control and becomes an optimisation — per-region digest and
poll cost, and a regional page that lists only what it holds. If it slips,
nothing leaks.

The secret never appears in the admin UI either, which continues to render the
reference. Only the hand-off to an agent carries a resolved value, to agents in
the region entitled to it.

### Open decisions

- **Where resolved values come from.** Recommended first cut: environment
  indirection, matching `token_env` exactly — no new storage, no new admin
  surface, provisioned with the deployment. A region-local secret store managed
  at runtime is the later upgrade if credentials need rotating without a
  restart; its one rule is that values never cross a region boundary.
- **What an unresolved reference does to a check.** It must not silently probe
  with a literal `${...}` or quietly go idle. Recommended: the check reads as a
  configuration error naming the missing reference, in the same spirit as
  `missing_token_error`.

## Production security and recovery boundaries

This section records required deployment semantics and operator procedures. It
is not an implementation claim: the controls and recovery automation described
below remain production-readiness work unless the running deployment provides
and tests them.

### SSL expiry probes and TLS validation

An SSL certificate-expiry probe obtains the peer certificate and reports its
validity dates. It intentionally does **not** establish that the presented
certificate chains to a trusted issuer or that its names match the configured
host. Consequently, an expiry result answers only whether the observed
certificate is near expiry; it must not be interpreted as an HTTPS trust or
hostname-validity result. Redirects, proxies, SNI selection, and load balancer
certificate choice must be made explicit in the probe configuration and test
plan so operators know which peer certificate is being observed.

If certificate trust and hostname validity become probe outcomes, report them
as separate failure classes from expiry: `expired`/`expiring`, `untrusted
chain`, and `hostname mismatch`. Do not fold an untrusted or mismatched
certificate into an expiry failure, and do not turn the expiry probe's current
non-validating collection path into a claim that a target is secure. The
per-check `allow_self_signed` behavior is unresolved, so no deployment should
rely on that option until its HTTP-client semantics and tests are implemented
or the option is removed.

### Network authority, ingress, and credentials

A monitor target and a notifier webhook deliberately grant the service
server-side network authority. An administrator who can create or modify either
can direct probes or notifications at internal addresses, cloud metadata
endpoints, control-plane services, or external destinations. Treat admin access
as network-level privilege, not merely UI configuration access; restrict it to
trusted operators, use least-privilege service identities, and audit changes to
targets, webhooks, and credential references.

For multi-tenant or hostile-input deployments, enforce egress outside the
application until an application policy exists: deny private, loopback,
link-local, multicast, and metadata ranges by default; constrain DNS resolution
and rebinding; allow only approved destination CIDRs/hostnames and ports; and
separate monitor/notifier egress from database, peer, and management networks.
Firewall, network-policy, proxy, or dedicated egress-gateway controls should
also bound outbound DNS, HTTP(S), SMTP, and webhook traffic. These mitigations
are not presently represented as a complete in-application SSRF policy.

Terminate public TLS at a managed ingress or reverse proxy, or configure TLS on
the service directly. Redirect HTTP to HTTPS, protect cookies and bearer tokens
in transit, validate the public certificate and hostname, and restrict direct
backend listener access to the trusted proxy/network. Do not enable forwarded
protocol, host, or client-address headers unless the immediate proxy is
explicitly trusted and strips client-supplied copies.

Login rate limiting keys on the raw socket peer address by default, and still
does behind a reverse proxy that is not declared: every user of that proxy
shares one bucket, and `X-Forwarded-For` is not trusted as a workaround. Set
`trusted_proxies` (`[coordinator]`/`[global]`, exact IPs or CIDRs) to change
that — `crate::security::client_ip` then reads the forwarded header from the
immediate peer only when it is in that list, walking it from the right and
skipping entries that are themselves trusted proxies, so a client cannot
prepend a fake hop ahead of what the real chain appended. The default is
unchanged (empty list, header ignored) whether or not this is configured, so
an operator who does not set it keeps exactly the shared-bucket behaviour
above. See `security::tests` and `admin_api::a_trusted_proxys_forwarded_for_is_honoured_per_client`.

Credential references keep values out of replicated check documents, but they
do not eliminate rotation work. Rotate admin, peer, global, agent, SMTP, and
webhook credentials with an overlap plan: provision the replacement in every
consumer and region, reload or restart only the affected consumers, verify new
requests authenticate, revoke the old value, and audit for failed or stale
clients. Never place values in check documents, replication payloads, admin
read responses, logs, backups with broad access, or screenshots. Rehearse this
procedure before relying on it during an incident.

### Checkpointed DuckDB backup, restore, and peer recovery

A safe offline backup is a consistent copy made only after writes are stopped
or the database is otherwise closed to this process, the DuckDB checkpoint has
completed successfully, and the database and any required sidecar state are
copied as one backup generation. Do not copy a live database file and call it a
backup. Write the copy to separate durable storage, record version, timestamp,
source node, file size, checksum, retention tier, and restore instructions, and
verify its checksum after transfer. Resume service only after the checkpoint and
copy complete; a planned maintenance window or a replica-specific offline
backup avoids silently racing active writes.

Restore into a fresh, isolated directory or replacement node rather than over a
live database. Keep the original database untouched until the restored process
opens it cleanly, required schema/data checks pass, known current states and
history samples agree, and the service can ingest and query normally. Verify a
backup on a recurring schedule with an actual restore, not only a successful
file copy. The target schedule is 7 daily, 4 weekly, and 12 monthly snapshots;
apply immutable/off-site storage and access controls appropriate to the loss
scenario. This schedule is operator-managed, not a built-in scheduler.

`warden backup --config warden.toml --output <path>` and
`warden restore --from <backup> --into <path>` are the built-in procedure for
the two paragraphs above, run as a separate CLI invocation rather than an
admin HTTP route: streaming a multi-gigabyte database through an admin session
is the wrong shape for an operator action this size, and a backup command that
opens `coordinator.db_path` directly gets DuckDB's own single-writer file lock
for free as the enforcement of "stop writes first" — it fails immediately
against a coordinator that still holds the file, rather than needing an
in-process pause it would otherwise have to invent. `backup` checkpoints the
source, copies the file (and its WAL sidecar, if one is still present because
the checkpoint and the copy raced a write), reopens the copy to prove it is
queryable rather than merely present, and writes a manifest recording version,
timestamp, source node, file size, and checksum beside it. It refuses to
overwrite an existing destination: a backup generation is immutable once
written. `restore` copies a backup into a fresh destination, verifies the
manifest checksum before trusting it, and reopens the result to read raw
result counts, current-state rows, and the oldest retained result — the same
"opens cleanly and reads back what it should" check `restore` always asks for,
run automatically instead of by hand. It refuses to write over an existing
path for the same reason SCALING.md tells an operator not to: restore into a
replacement location, never over a live database. Neither command drives the
7/4/12 schedule, the durable-storage placement, or the peer-level checks
below; those remain operator- and cluster-level responsibilities.

A peer that has been offline longer than raw-result retention cannot obtain a
complete raw history through normal anti-entropy. Recovery must choose and
record one of two explicit outcomes: restore a verified snapshot sufficiently
recent to rejoin through retained replication history, or rejoin with a marked
raw-data gap while retaining/repairing current state and state-transition data.
Before returning the peer to service, verify database integrity/openability,
backup checksum, schema compatibility, replication cursor/manifest position,
current-state convergence, expected raw-retention boundary or declared gap,
and ingest/query health. Do not reduce raw retention or advertise peer recovery
as supported until this path has been exercised under the configured retention
policy.

## Production observability

`GET /metrics` on a coordinator (and, for the subset that applies, a global
node) exposes OpenMetrics samples over the counters `Timings`/`Metrics`
already accumulated in-process — atomics only, no lock or extra query per
scrape (`Coordinator::metrics`, `database::Database::metrics_snapshot`).
Every series below is low-cardinality by construction: no check id, agent id,
or peer id ever appears as a label, only bounded, admin-known sets (a
membership `state`, for example).

- **Database latency and lock wait**: `warden_database_queries_total`,
  `warden_database_query_duration_seconds_total` (execution),
  `warden_database_queue_wait_seconds_total` (time queued behind the single
  worker before execution — the "lock wait" half), and
  `warden_database_queue_depth` (current backlog, gauge). Alert on
  `queue_depth` sustained near 256 (`QUEUE_CAPACITY`) — SCALING.md's own
  "Read path" section documents that overrunning this queue turns into
  backpressure on result ingest — or on `queue_wait_seconds_total` growing
  faster than `queries_total` (jobs increasingly wait rather than run).
- **Ingest backpressure**: `warden_ingest_inflight` (gauge, concurrent
  `ingest` calls admitted) and `warden_ingest_rejected_total` (batches shed
  once `MAX_INGEST_INFLIGHT` — 256, matching the database queue's own budget
  — is already reached). Any nonzero rate on the rejected counter means the
  coordinator is shedding agent data under overload; alert on it directly
  rather than waiting for the queue-depth signal above.
- **Replication health**: existing `warden_replication_raw_data_gaps_total`
  and `warden_replication_alert_identity_conflicts_total`, plus
  `warden_replication_anti_entropy_failures_total` (a sweep that never
  reached reconciliation: no reachable peer, a malformed response, or a
  failed local digest read) and
  `warden_replication_anti_entropy_last_success_timestamp_seconds` (unix
  seconds, gauge). Alert on `time() -
  warden_replication_anti_entropy_last_success_timestamp_seconds` exceeding
  a few multiples of `anti_entropy_secs` — reconciliation lag stated
  directly, not inferred from the failure counter's absence.
- **Notification retry/give-up**: `warden_notification_retries_total` and
  `warden_notification_giveups_total`. A give-up means the admin panel's
  "nobody was paged" case actually happened; alert on any increase.
- **Cluster membership**: `warden_cluster_membership_transitions_total{state="suspect"|"dead"}`
  (counter, demotions only — a resurrection through gossip shows up in the
  gauge below on its own) and `warden_cluster_members{state="alive"|"suspect"|"dead"}`
  (gauge). Alert on `dead` staying above zero, or on a transition rate that
  outpaces expected restarts.
- **Retention**: existing `warden_retention_prune_duration_seconds_total`,
  plus `warden_retention_rows_removed_total`. Alert if a day passes with no
  movement on either — the daily job did not run — or if prune duration grows
  without bound relative to rows removed.

The global tier has no ingest, per-region replication, or retention of its
own, so its `/metrics` carries only what is cheap and meaningful there: the
same database series (it shares `coordinator::database::Database` verbatim
via `GlobalStore`) and, when `global.peers` is configured, the same cluster
membership series (it shares `coordinator::cluster::Cluster` verbatim too).
Global reconciliation is labelled by a fixed `scope="peer"|"region"`:
`warden_global_reconciliation_failures_total` (local digest read, digest
transport/status, or malformed response; a region counts once after every
endpoint fails), `warden_global_reconciliation_repair_failures_total` (a
repair after a valid comparison failed), and
`warden_global_reconciliation_last_success_timestamp_seconds` (last valid
digest comparison, recorded before repair). Region push staleness is derived
at scrape time from the cache's receiver-side timestamps, with no extra
state: `warden_global_regions_stale`, `warden_global_regions_never_received`,
and `warden_global_max_received_push_age_seconds` (0 when no region has
pushed). Only global-a receives pushes in the Compose fixture, so the
staleness gauges are meaningful there only.

## Scaling milestones

### Now: identity correctness

- UUIDv7 and native UUID schema.
- Unicode mutable names.
- No file-seeded checks.
- UUID-based relationships and global identity.

### Next: eliminate known amplification

- Deterministic schedule spreading and bounded concurrency.
- Cached placement and delta assignment polling.
- Materialized current status and set-based bounded queries.
- Compressed HTTP, concurrent peer fan-out, and bounded retries.
- Incremental regional/global streams and anti-entropy metadata.

### Then: prove the target

- Build the benchmark harness.
- Load 30 days of representative data.
- Test steady state, synchronized failures, partition loss, catch-up, and retention.
- Publish a supported envelope for checks, domains, cadence, probe type, and retention.

### Later: storage evolution if measurements require it

- Time-partition raw observations.
- Reduce raw-result replication independently of control/state replication.
- Move raw observations to object or dedicated time-series storage while retaining DuckDB for control and analytical reads.
- Consider gRPC only after incremental protocol behavior is correct and transport overhead is measured as material.
